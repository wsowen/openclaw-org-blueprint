# BANK_LEDGER_RUN_PROTOCOL.md

## 目标

这份协议用于约束 `Iris / Finance Operations Lead` 在处理“银行流水 Excel -> 候选分录草稿”任务时的标准执行方式。

它定义的是：

- OpenClaw 该如何接任务
- 必须产出哪些结果
- 哪些判断可以直接给出
- 哪些情况必须停下来请求人工确认

## 适用任务

当用户提出以下类型任务时，应优先遵循本协议：

- 把银行流水整理成记账分录草稿
- 处理 `.xls` / `.xlsx` 银行台账
- 输出银行流水标准化结果
- 生成候选业务分类与人工复核清单

## 当前核算前提

- 当前企业为小规模纳税人
- 当前默认适用小企业会计准则
- 如果后续升级为一般纳税人或切换为企业会计准则，应同步更新候选科目映射与说明口径

## 标准执行步骤

### Step 1. 明确输入与范围

至少先确认以下信息：

- 原始文件路径
- 工作表名称或默认使用全部相关 sheet
- 时间范围
- 账户主体
- 本次目标是“标准化”“归类”“分录草稿”“人工复核”中的哪些输出

如果输入缺少时间范围或主体信息，允许先处理，但必须在最终结果中明确提示限制。

### Step 2. 检查原始文件结构

处理前必须先确认：

- 真正的表头所在行
- 日期字段
- 收支方向字段
- 金额字段
- 余额字段
- 摘要、用途、备注、对方主体等辅助字段

如果文件结构混乱，应先输出字段映射说明，再继续处理。

### Step 3. 生成标准化流水表

必须按照 `STANDARD_FIELDS.md` 输出标准字段。

最低要求：

- 每条流水可追溯到原始文件、sheet、行号
- 统一 `normalized_direction`
- 统一 `net_amount`
- 保留原始摘要、用途、备注
- 对缺失关键字段的行标记人工复核

### Step 4. 执行业务归类

必须按照 `BUSINESS_CLASSIFICATION.md` 输出：

- `business_type_candidate`
- `classification_confidence`
- `classification_basis`
- `requires_manual_review`
- `manual_review_reason`

归类时优先级如下：

1. 已确认的主体/规则映射
2. 样本驱动的稳定规则
3. 通用关键词与方向规则
4. 无法稳定判断时进入 `other_or_unknown`

### Step 5. 生成候选分录草稿

必须按照 `JOURNAL_DRAFT_TEMPLATE.md` 输出候选分录，而不是正式凭证。

允许直接产出高置信候选分录的前提：

- 业务分类清晰
- 金额方向清晰
- 对方主体或业务用途足够明确
- 不涉及资本口径、冲销逻辑或复杂例外

在当前公司口径下，以下场景应优先这样理解：

- `代发工资`、社保、公积金等银行付款流水：优先作为已计提后的支付动作处理
- `1688` / 支付宝渠道供货款：在业务方已确认背景时，可按 `vendor_payment` 处理
- 小额企业账户来款且符合开户/验证场景：可按 `verification_deposit` 处理

### Step 6. 生成人工复核清单

必须按照 `MANUAL_REVIEW_TEMPLATE.md` 输出人工复核项。

以下情况默认进入人工复核：

- 对方为个人但用途不清
- 支付通道类交易无法映射到真实业务
- 工资批量支付缺少工资明细
- 股东注资、借款、往来款等资本性质待确认
- 退款、冲销、异常大额或多规则冲突

## 标准输出包

一次完整执行，建议至少产出：

- 标准化流水表
- 业务归类结果表
- 高置信候选分录表
- 待人工复核分录表
- 人工复核清单
- 一份简短执行摘要

## 最终回复用户的格式要求

`Iris` 在完成一次处理后，回复中至少要说明：

- 处理了多少条流水
- 高 / 中 / 低置信度各多少条
- 哪些业务类型最常见
- 有多少条进入人工复核
- 最值得用户拍板的事项是什么
- 哪些结论是候选草稿，不能视为正式入账

## 禁止事项

处理该类任务时，禁止：

- 把候选分录写成正式财务结论
- 在证据不足时强行归类
- 用猜测补齐业务对手方
- 用估计值替代原始金额
- 跳过人工复核直接输出正式记账意见

## 升级与回写

当人工确认完成后，应优先把确认结果回写到：

- `ENTITY_RULES.md` 中的主体映射
- 稳定关键词规则
- 强制人工复核规则

目标是让 `Iris` 随着真实业务样本不断提高稳定性，但仍保持“有依据、可追溯、不编造”。
